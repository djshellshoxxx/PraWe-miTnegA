# PRIOR-ART-ACADEMIC — research literature relevant to RevocationGap

### A1. Pang et al., "Zanzibar: Google's Consistent, Global Authorization System", USENIX ATC 2019, pp. 33–46 — CA-S040 (S)
- **Establishes:** the **"new enemy" problem** — unauthorized access when ACL updates and content updates are applied out of causal order, or old ACLs apply to new content (examples: remove Bob then add content; check evaluated with a stale ACL from before Bob's removal). **Zookies** (opaque consistency tokens encoding a timestamp) give *at-least-as-fresh* semantics: Zanzibar may evaluate at any timestamp ≥ the zookie, so most checks use default (bounded) staleness. Availability is **measured with probers that replay sampled live requests**, adjusting the zookie so relative age is preserved, 3 probers per cluster with outliers excluded.
- **Lesson:** (1) Model "revocation took effect" relative to a **causal reference point** (the event's commit/ack time), not wall-clock alone; capture the IdP's acknowledgement of the admin action as the t₀ anchor. (2) Staleness is a *designed property* of many authorization systems — the outcome classifier needs an "expected bounded staleness" class (documented delay) distinct from "vulnerability". (3) Use **multiple independent probers and outlier handling** rather than a single probe (maps to RG's N-consecutive-denial/confirmation rule). (4) Stateless JWT validation at an RS is the extreme "old ACL" case — expect it to be the dominant finding type.

### A2. Bailis, Venkataraman, Franklin, Hellerstein, Stoica, "Probabilistically Bounded Staleness for Practical Partial Quorums", VLDB 2012 — CA-S042 (S)
- **Establishes:** **PBS t-visibility** — with probability 1−p, a read started at least *t* time units after the last version committed returns that version (or newer); expresses staleness "with respect to both versions and wall clock time"; Monte-Carlo prediction with latency distributions; evaluation with Cassandra experiments and production operation-latency data.
- **Lesson:** Output for multi-replica / cached enforcement should be a **time-indexed probability P(access still allowed | t since event)** with a confidence interval, not a single "N seconds". Probing at several offsets *t* and repeating trials is the empirical analogue of PBS's Monte-Carlo curves. Report flapping (non-monotonic) explicitly. Also: PBS notes worst-case semantics give unfavourably low probabilities — decide whether RG reports typical-case or worst-observed (suggest both).

### A3. Atlidakis, Godefroid, Polishchuk, "Checking Security Properties of Cloud Service REST APIs", ICST 2020 — CA-S041 (V, full PDF read)
- **Establishes:** four REST security rules enforced by **active property checkers** on a stateful REST fuzzer: *use-after-free* (deleted resource must be inaccessible), *resource-leak*, *resource-hierarchy*, *user-namespace* (resource created under one token must not be accessible with another token). Active (generates new tests to break the rule) vs passive (monitors only); checkers are mutually exclusive by precondition (DELETE ⇒ UAF checker; 4xx ⇒ leak checker …); per-checker **bug bucketization** by request-sequence suffix; "optimized" vs "exhaustive" modes. Production Azure/Office365 bugs found. Also observes that services **delay responses to failed requests as throttling**, and that DELETE vs failed requests differ in latency.
- **Lesson:** This is the intellectual ancestor of Schemathesis' `use_after_free` — it shows exactly what is **missing**: the rules are *spatial/lifecycle* with no time axis, and expectation is fixed ("4xx"). RG should (1) adopt the **active-checker pattern** (the tool itself triggers the state change and tries to violate the rule), (2) keep checkers modular with exclusive preconditions and per-checker finding buckets, (3) **record per-response latency** because denied responses may be deliberately slowed — a timing artifact that could distort window estimates, (4) note the "user-namespace" checker (replay with another identity's token) as the pre-event control probe.

### A4. Fett, Küsters, Schmitz, "A Comprehensive Formal Security Analysis of OAuth 2.0", ACM CCS 2016, pp. 1204–1215 (arXiv:1601.01229) — CA-S043 (S)
- **Establishes:** first extensive formal analysis of OAuth 2.0 in the FKS Dolev-Yao web model; four attacks found, fixes proven. **Stated limitation:** the model does **not** cover expiration of access tokens or session IDs, **revocation of access tokens, or user log-out** (it over-approximates by not expiring tokens).
- **Lesson:** Formal guarantees (authorization, authentication, session integrity) say **nothing** about post-event continued access, so empirical testing is not redundant with formal work; RG's findings should be positioned as *deployment/enforcement* properties orthogonal to the proven protocol properties. (Fett et al.'s later OIDC/FAPI analyses — see leads — were not read; do not assume they close this gap.)

### A5. RFC 9700 — Best Current Practice for OAuth 2.0 Security (BCP 240), Jan 2025 — CA-S038 (V, §4.14 read in full text)
- **Establishes:** refresh tokens let servers issue short-lived access tokens; for **public clients** the AS **MUST** detect refresh-token replay via sender-constraining **or rotation** (reuse of an invalidated token ⇒ revoke the active token); AS **MAY** revoke refresh tokens on password change or logout; refresh tokens SHOULD expire on inactivity; §4.2.4 restates RFC 6749's recommendation that on redeeming an authorization code twice the AS SHOULD revoke all tokens previously issued from that code. **No requirement** to revoke already-issued access tokens; no numeric access-token lifetime.
- **Lesson:** Defines the **protocol-expected baseline** for the outcome classifier: "access token still works after refresh-token revocation" is *expected protocol semantics* unless the deployment claims otherwise; "old refresh token accepted after rotation (public client)" is a *real violation*. The classifier needs per-requirement strength (MUST/SHOULD/MAY) as a field.

### A6. Ghasemisharif, Ramesh, Checkoway, Kanich, Polakis, "O Single Sign-Off, Where Art Thou? An Empirical Analysis of Single Sign-On Account Hijacking and Session Management on the Web", USENIX Security 2018, pp. 1475–1492 — CA-S045 (S)
- **Establishes:** IdP account compromise cascades to RPs; evaluates attacks against **95 major web/mobile services**; examines what session/account-management options users have to *recover* (e.g., sessions not logged out after credential changes; account-linking persistence) and proposes **Single Sign-Off** (OIDC extension to revoke access across all RPs of a hijacked IdP account).
- **Lesson:** The threat model for RG scenarios: "attacker keeps access after the victim/admin remediates". Scenario catalogue should include *remediation actions* (password change, "sign out everywhere", unlink/deauthorize app, disable account) × *artifact types* (cookie, bearer, refresh token) — and test which combinations really terminate access. Supports the "cross-service" differentiator (RPs behave very differently).

### A7. Ghasemisharif, Kanich, Polakis, "Towards Automated Auditing for Account and Session Management Flaws in Single Sign-On Deployments" (SAAT), IEEE S&P 2022 — CA-S044 (S)
- **Establishes:** modular automated framework (account-creation engine + auditing pipeline) for RPs using Facebook as IdP; its **revocation test (Algorithm 2)**: log into all RPs via SSO → **remove the RPs from the IdP using a `Revoke` module** → use a `Detection` module to determine logged-in vs logged-out state; steps are separated and run in parallel to allow **repeating incomplete steps** and to avoid being **banned for sending too many requests** to the IdP.
- **Lesson:** Validates the architecture RG needs: separate **orchestrate (Revoke)**, **act-as-victim (Login)**, **state detection (Detection)** modules; make each step idempotent/retryable; budget IdP-side request rates. The detection step is the weak point (login/logout state inferred from cookies) — RG's *enforcement-signal parser* generalises it. Limitation to avoid: SAAT checks state once; RG needs a series.

### A8. Lamisa, Mannan, Youssef, "Login, Logout, Reset: Measuring Security and Privacy Issues in Real-World Web Logins" (LoginPlus), SecureComm 2025, LNICST 688, pp. 41–68 (online 2026-05-19) — CA-S046 (V abstract + appendices/refs; body paywalled)
- **Establishes:** automated registration/login/password-recovery over the CrUX top-1M; **85 %** of sites using JWTs for authorization fail to invalidate tokens on logout; 2.67 % use email-link logins and 48 % of those fail to invalidate links after 24 h; 13 % of recovery links stay valid after use; **51 %** do not terminate prior sessions after password reset. Appendix D re-tests cookie invalidation: of 5,642 sites with successful logout, **513 (9 %)** did not invalidate the cookie; **re-tested after 24 h: 325 still accepted; after 7 days: 203**; earlier work (Calzavara et al.) reported 18 %. Maps checks to OWASP ASVS (logout invalidates session tokens; stateless tokens use signatures; terminate other sessions after reset). Its related-work survey lists JWT revocation designs (short-lived, blacklist, secret rotation).
- **Lesson:** (1) **Base rates** justify the product (but are consumer-web, not IdP-managed APIs — transfer is (I)). (2) **Long-horizon re-test** (24 h, 7 d) is an accepted methodology and shows "still valid" can persist for days — RG schedules need a long-tail mode (cheap, sparse probes), not only second-scale polling. (3) Counting "does not invalidate" as a *failure* conflates design-intended stateless tokens with bugs — exactly the classification problem RG must solve (A5/A11). (4) ASVS requirement IDs are a ready mapping for expectation policy.

### A9. Philippaerts, Preuveneers, Joosen, "OAuch: Exploring Security Compliance in the OAuth 2.0 Ecosystem", RAID 2022, pp. 460–481 — CA-S016 (S) + tool source CA-S015 (V)
- **Establishes:** **113** test cases derived from threat model/BCP/spec requirements, run against **100 public IdPs**; on average an IdP lacks 20 % of *required* and 33 % of *all* security specifications; the authors contrast OAuch (security-focused, any requirement level, includes BCP) with the OIDF certification tests (conformance-focused). Tool source (V): revocation tests with a fixed 5-s wait; a resumable time-delayed test (`ITimeDelayedTest`); outcome enum per spec requirement.
- **Lesson:** Prior art for **requirement-mapped test IDs and an outcome enum**, and for **dependency-ordered tests** (revocation tests depend on a "flows supported" result). RG should interoperate (import OAuch results as context) and *exceed* it on timing. The 5-s fixed wait is a concrete weakness to cite: a revocation that completes at 6 s is reported as "not implemented" (harsh false failure), while 1 s and 4.9 s lags are indistinguishable (both "fully implemented").

### A10. OpenID Connect Back-Channel Logout 1.0 (final, errata set 1) — CA-S048 (S); with OIDF logout conformance modules — CA-S013 (V)
- **Establishes:** OP posts a signed `logout_token` to the RP's `backchannel_logout_uri`; **RPs must implement an application-specific method of terminating RP sessions** ("more complicated than simply clearing cookies"); OPs encouraged to use logout-token lifetimes ≤ 2 minutes; the RP URI must be reachable from the OP. OIDF OP tests verify the OP sends a valid token and that `prompt=none` then fails; RP tests verify the RP's response to valid/invalid logout tokens (V).
- **Lesson:** "Logout" is at least three layers — OP session, RP session, and **already-issued access/refresh tokens at resource servers** — and conformance suites cover only the first two (the one exception — OIDF's warning-level check that the access token from a *reused authorization code* is revoked after a fixed 30 s — is a single probe). RG's scenario model should keep these layers separate in evidence (*which* layer still allowed access), and treat delivery of the logout token as observable (RG can host a back-channel endpoint in the lab).

### A11. OpenID SSF 1.0 / CAEP 1.0 (Final, Aug–Sep 2025) — CA-S022/S023/S025 (S)
- **Establishes:** SSF: SETs MUST NOT contain `sub` or `exp`; "each deployment or integration [may] define its own event processing behaviors, **ranging from informational input … to mandatory enforcement**"; CAEP `session-revoked` has **no event-specific claims**; when `event_timestamp` is present it **MUST represent the time the revocation occurred**.
- **Lesson:** (1) Whether a receiver must *enforce* is not in the standard — the expectation policy must be an explicit per-deployment input (otherwise "CAEP event delivered but access continued" is not automatically a violation). (2) Use `event_timestamp`/`iat` of the delivered SET as the **t₀ anchor for the CAEP path**, and measure delivery→denial separately from event→delivery (two latencies). (3) SETs lack `exp`, so replay/ordering protection must be tested through `jti`/`iat`, not expiry.

### A12. Microsoft Entra Continuous Access Evaluation docs (industry reference) — CA-S033 (S)
- **Establishes:** CAE lets a resource provider reject a non-expired token; client learns via **401 + claims challenge** (`error="insufficient_claims"`, base64 `claims`); in CAE sessions the configurable token-lifetime policy is not honoured and **lifetime rises to up to 28 h**; for Global Secure Access, disabling a user invalidates refresh tokens immediately but access tokens take up to 90 minutes to expire absent Universal CAE. Vendor test guidance is manual (revoke the session in the portal).
- **Lesson:** Provider-specific **enforcement signals** and **documented delays** exist and must be encoded as expectation data (with the doc's own caveats and doc version/date), e.g. a 401 carrying a claims challenge is *the* CAE enforcement signature; a plain 401 from an expired token is not. Also: long-lived CAE tokens are an intended design — classify "still valid 20 min after revoke" differently on CAE vs non-CAE resources.

### A13. NIST IR 8587 (final, 2026-09-15), "Protecting Tokens and Assertions from Forgery, Theft, and Misuse" — CA-S039 (S: announcements only; report text NOT read)
- **Establishes (per announcements):** guidance for CSPs/agencies on IdP/AS architecture, token verification and lifecycle controls; press summary reports access/identity tokens should live ≤ 1 hour and expired tokens must be rejected by authorization services/PEPs (U on exact wording); the OpenID Foundation says it participated directly in developing the guidance and its SSF WG co-chair commented (CA-S039, snippet).
- **Lesson:** Regulatory demand for *evidence* of token lifecycle behaviour → RG's evidence timeline has a compliance audience. Action: read the report text before encoding any numeric expectation.

### A14. OWASP WSTG-SESS-06 "Testing for Logout Functionality" — CA-S047 (S)
- **Establishes:** manual procedure: replay the authentication artifact (cookie/bearer) after logout, including **from a second device**; "Logout must invalidate the authentication artifact server-side … Access must not remain valid until authentication artifact expiration"; notes cookie-only frameworks (e.g., ASP.NET Forms Auth) cannot revoke by design; SSO logout may not propagate.
- **Lesson:** The canonical manual test that RG automates; shows the community's **default expectation is strict invalidation** — which is why RG's policy layer must make "expected" explicit rather than inheriting WSTG's absolute stance for stateless tokens.

### Cross-cutting synthesis (I)
1. **Measurement methodology** to adopt: anchor at the acknowledged event time; probe at geometric then sparse long-horizon offsets (seconds → days, per A8); repeat trials; report P(allowed | t) with intervals (A2); keep independent probers/outlier handling (A1); log response latency (A3).
2. **Expectation model:** requirement strength from RFC 9700/ASVS (A5, A8), provider docs (A12), deployment-defined CAEP enforcement (A11) → classes *expected / documented delay / risky config / vulnerability / needs verification / inconclusive*.
3. **Architecture:** orchestrate/act/detect module split with retryable idempotent steps and IdP rate budgets (A7); active-checker pattern with exclusive preconditions and per-checker finding buckets (A3).
4. **Gaps confirmed in the literature:** formal OAuth analyses omit revocation/logout (A4); conformance suites test delivery/OP-session not RS enforcement (A10, COMPETITIVE-ANALYSIS §1.6); measurement studies are single-time-point or coarse (24 h/7 d) (A7, A8).
