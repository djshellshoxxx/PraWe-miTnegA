## 2. Per-standard sections

### STD-003 RFC 7009 — Token Revocation (V, full)

**Requirements relevant to revocation/temporal testing**
- §2: Implementations **MUST support revocation of refresh tokens** and **SHOULD support revocation of access tokens**.
- §2.1: `token` REQUIRED; `token_type_hint` OPTIONAL — server **MUST** search all supported types if hint fails; server MAY ignore hint; an invalid hint value is ignored and does not affect the response (§2.2).
- §2.1: AS first authenticates the client and verifies the token was issued to that client; if that fails the request is refused with an error.
- §2.1: "The invalidation takes place immediately, and the token cannot be used again after the revocation." but, same paragraph: in practice there "could be a propagation delay" where some servers know and others don't; implementations "should minimize that window". Clients "must not try to use the token after receipt of an HTTP 200".
- §2.1: Cascade is policy-dependent. If the token is a **refresh token** and the AS supports AT revocation, the AS **SHOULD** also invalidate all ATs of the same grant. If the token is an **access token**, the server **MAY** revoke the refresh token as well. The text says differing cascade policies "should not pose interoperability problems".
- §2.2: **HTTP 200** if the token was revoked **or if the client submitted an invalid token** (rationale: purpose already achieved). Response body ignored.
- §2.2.1: error `unsupported_token_type` = server does not support revoking this token type (e.g., AT revocation unsupported). **HTTP 503** ⇒ client must assume the token **still exists**; MAY retry (Retry-After).
- §3 (Implementation Note): with self-contained tokens, immediate AT revocation needs "(currently non-standardized) backend interaction" between AS and RS; alternative is short-lived ATs refreshed via RT, which bounds the revoked-but-usable window.
- §5: if AT revocation is unsupported, ATs "will not be immediately invalidated" when the RT is revoked; deployments must account for it.

**Implementation-defined / unspecified (continued access can be legitimate)**
- Whether ATs are revocable at all (SHOULD only). Whether RT revocation kills ATs (SHOULD, only if AT revocation supported). Whether AT revocation kills RT (MAY). Size of the "propagation delay" (unquantified). How an RS learns of AT revocation for self-contained JWTs (non-standardized).
- Not defined: revocation of the user's session, of *other* grants, or of tokens in response to user/role changes.

**Testable observations** — revocation response code (200 / 4xx `invalid_client`/`invalid_request` / `unsupported_token_type` / 503); subsequent introspection `active`; subsequent RS response (401 `invalid_token` vs 2xx); refresh attempt result; time-to-convergence of RS acceptance.

**RevocationGap implications** — 200 is **not evidence of revocation** (also returned for garbage tokens). Always follow with an independent state check. `unsupported_token_type` on an AT is a *compliant* negative capability, not a defect. A short post-200 window where an AT still works is spec-acknowledged "propagation delay"; the tool must measure duration, not just binary acceptance.

### STD-004 RFC 7662 — Token Introspection (V, full)

**Requirements**
- §2.2: response `active` is REQUIRED boolean. Its meaning "will vary depending on the implementation" but generally means issued by this AS, not revoked by the resource owner, and within its validity window.
- §2.2: if call is authorized but token is not active / unknown / RS not allowed to introspect it, AS **MUST** return `{"active": false}` with HTTP 200; AS **SHOULD NOT** include other information or the reason (also §4).
- §2.3: invalid RS credentials ⇒ **401** (client creds → RFC 6749 §5.2; bearer → RFC 6750 §3). Inactive/unknown token is **not** an error.
- §2.1: endpoint **MUST** require authorization (client auth or bearer token); if AS can't determine state without more info, it **SHOULD** answer `active:false`.
- §4: AS **MUST** perform all *applicable* checks: expiry, not-yet-valid (nbf), **revocation**, signature, audience/RS eligibility.
- §2.2/§4: RS **MAY cache** responses, trading liveness for performance; caching can create a window where a revoked token is accepted; "MUST NOT be cached beyond" `exp` if present. Highly sensitive deployments can disable caching.
- Optional response members: scope, client_id, username, token_type, exp, iat, nbf, sub, aud, iss, jti (+ extensions).

**Unspecified** — definition of "active" beyond the above; cache TTL; whether user-disabled / role-removed / session-ended makes a token inactive; whether AS answers differently per RS (explicitly allowed).

**Testable observations** — `active` flips true→false; extra fields on inactive responses (SHOULD NOT); RS behaviour vs. AS introspection (divergence ⇒ RS cache or local-only validation); introspection 401 (tester credential problem, not token state).

**Implications** — Introspection is the tester's **ground-truth oracle** for opaque tokens *when the tester is itself an authorized introspecting client*. It is the AS's view, not the RS's; RS acceptance must be probed separately. Treat AS-active=false & RS-accepts as an RS-side enforcement gap (cache or local validation).

### STD-002 RFC 6750 — Bearer Token Usage (V, full)

**Requirements**
- §3: if a request lacks credentials or has a token that doesn't grant access, RS **MUST** send `WWW-Authenticate` (scheme `Bearer`). If a token was presented and failed, RS **SHOULD** include `error`.
- §3.1: `invalid_token` = "expired, revoked, malformed, or invalid for other reasons" → **SHOULD** be HTTP **401**; `insufficient_scope` → SHOULD be **403**; `invalid_request` → SHOULD be **400**. Without any auth info the RS SHOULD NOT include an error code.
- §5.2: token lifetime **MUST** be limited; short-lived (one hour or less) tokens reduce leak impact. §5.3: servers **SHOULD** issue short-lived (one hour or less) bearer tokens; SHOULD audience-restrict. Bearer tokens **MUST NOT** be stored in cookies that can be sent in the clear.
- §2.3: query-parameter method SHOULD NOT be used (MAY be supported by RS); 9700 tightens this for clients (STD-008).

**Unspecified** — what the RS does to decide validity (introspection, local signature, DB lookup); "short" is a SHOULD with a one-hour example, not a hard bound; no revocation mechanics.

**Testable** — status code + `WWW-Authenticate` parse (`error`, `error_description`, `scope`). **Implications** — use `invalid_token`/401 as the canonical "credential rejected for token reasons" signal; 403 `insufficient_scope` indicates authentication succeeded but authorization (scope) failed — important to distinguish *role removed* (authorization change) from *token revoked* (authentication change). Servers frequently deviate (e.g., 403 for revoked) — classify as `needs verification`, not as "still valid".

### STD-005 RFC 7519 — JWT (V, full)

**Requirements**
- §4.1.4 `exp`: JWT **MUST NOT** be accepted on or after `exp`; implementers **MAY** allow "some small leeway, usually no more than a few minutes" for clock skew.
- §4.1.5 `nbf`: MUST NOT be accepted before `nbf`; same leeway allowance. §4.1.6 `iat`: informational age. §4.1.7 `jti`: unique ID, "can be used to prevent the JWT from being replayed"; use is OPTIONAL.
- §4.1: none of the registered claims is mandatory in all cases; applications define which are required. All registered claims OPTIONAL at the base-spec level.
- §7.2: validation steps incl. signature; any failed step ⇒ reject. "Application decision" which algorithms are acceptable.
- §4: unknown claims MUST be ignored unless the application says otherwise.

**Unspecified** — leeway number; any replay store for `jti`; revocation; what `iat` freshness window is acceptable.

**Testable** — decode token (without trusting it) and read `exp/nbf/iat/jti`; compute `remaining_ttl = exp − t_now(server-aligned)`; compare acceptance at `exp ± δ`.

**Implications** — A JWT accepted *before* `exp` after upstream revocation is **not** a standards violation (see STD-007). Acceptance *after* `exp + leeway` **is** a MUST violation (SV-001). Leeway is unquantified: classifier needs a configurable tolerance with an "ambiguous zone" (default proposal: ≤60 s clear-violation boundary beyond tolerance; 60–300 s ambiguous; >300 s violation, per "a few minutes").

### STD-007 RFC 9068 — JWT Profile for OAuth 2.0 Access Tokens (V, full)

**Requirements**
- §2.1: JWT ATs **MUST** be signed; MUST NOT use `none`; `typ` header MUST be `at+jwt` (or `application/at+jwt`).
- §2.2: REQUIRED claims: `iss, exp, aud, sub, client_id, iat, jti`. Optional `auth_time, acr, amr` (these "remain the same across all access tokens that derive from a given authorization response", including after refresh — §2.2.1). `scope` SHOULD be present if requested. `groups/roles/entitlements` SHOULD be used per RFC 7643 if included (§2.2.3.1).
- §4 RS validation (MUST): `typ`, exact `iss`, `aud` contains RS identifier, signature (reject `none`), and **current time before `exp`** (small leeway MAY). Any failure ⇒ `invalid_token` per RFC 6750 §3.1.
- §5: ID tokens must not be accepted as ATs (typing; RFC 8725 §2.8).

**Unspecified / key point** — §4 contains **no revocation or introspection step**. Local-only validation is fully conformant; the AS needs only to publish `jwks_uri`/`issuer`. Authorization attributes embedded in the token (roles/groups) are a snapshot at issuance.

**Testable** — header `typ`, claim set, JWKS rotation behaviour, `invalid_token` on failures.

**Implications** — "JWT still accepted after admin removed role / disabled user / revoked token" is **expected protocol semantics** up to `exp` unless the provider documents stronger enforcement (introspection at RS, token binding to session, `sid` checks). Report `remaining_ttl`, the configured lifetime, and whether RT/refresh then fails.

### STD-008 RFC 9700 — OAuth 2.0 Security BCP (V to §4.14)

**Requirements**
- §2.2.1: AS and RS **SHOULD** use sender-constraining (mTLS RFC 8705 or DPoP RFC 9449) for ATs. §4.10: ATs SHOULD be sender-constrained **and** audience-restricted; "architecture and performance reasons may prevent" it.
- §2.2.2: **Refresh tokens for public clients MUST be sender-constrained or use refresh token rotation** (§4.14). RFC 6749 already binds confidential-client RTs to the client.
- §4.14.2: AS **MUST** risk-assess whether to issue RTs; RTs **MUST** be bound to consented scope/RS; for public clients AS **MUST** use sender-constrained RTs **or** rotation. Rotation: new RT with every refresh; previous RT invalidated (relationship retained); if an old RT is presented, AS "cannot determine which party" used it but "will revoke the active refresh token" (forces re-grant). AS **MAY** revoke RTs automatically on **password change** or **logout at the AS**. RTs **SHOULD** expire after client inactivity (duration AS discretion).
- §4.14.1: RFC 6749 baseline for RTs includes confidentiality, TLS, client binding, unguessability; RFC 6749 "lays the foundation" for expiry/revocation/rotation (implementation-specific).
- §4.2.4: auth codes **MUST** be invalidated after first use; on double redemption AS **SHOULD** revoke previously issued tokens (restating RFC 6749 §4.1.2 (V)).
- §4.3.2: clients **MUST NOT** pass ATs in URI query (RFC 6750 §2.3 style).
- §2.3: ATs SHOULD be privilege-restricted and audience-restricted; RS MUST refuse tokens not meant for it.

**Unspecified** — grace period/“leeway” for concurrent refresh with rotation (not mentioned; implementations commonly add one — (U)); what happens to ATs on RT replay detection; AT lifetime numbers (only RFC 6750's one-hour SHOULD).

**Testable** — re-use of rotated-out RT (accepted? rejected? and does the *newest* RT die afterwards?); token response `token_type`/`cnf`; RT use from a second key (DPoP) or cert.

**Implications** — rotation reuse-detection tests (replay an old RT) are directly BCP-backed for public clients (MUST). For confidential clients rotation is optional, so acceptance of an old RT is **not** a violation. "MAY revoke RT on password change/logout" means survival of RT after a password change is *permitted*; flag as risky-config / needs-verification against provider docs, never "defect" from standards alone.

### STD-001 RFC 6749 — OAuth 2.0 (V §1–§4.2; §5.2/§6/§10.4 = S)

**Verified (V, read):** §1.5 — refresh tokens "intended for use only with authorization servers", issuance optional; §1.4 AT may be an identifier or self-contained; §4.1.2 — code MUST NOT be used more than once; on reuse AS MUST deny and SHOULD revoke (when possible) all tokens previously issued from that code; §3.2.1 — client authentication enables binding of refresh tokens to clients and recovery from a compromised client; §1.1 — AS/RS interaction is "beyond the scope"; §4.1.4 example token response carries `Cache-Control: no-store`.
**Second-pass, quoted via search snippets (S — primary RFC text could not be fetched past the truncation point; quotations taken from third-party pages and from the OAuth 2.1 drafts, which carry identical wording):**
- §5.2: token-endpoint errors use **HTTP 400** "unless specified otherwise"; `invalid_grant` = the provided authorization grant "or refresh token is invalid, expired, revoked, does not match the redirection URI used in the authorization request, or was issued to another client" (this is one code for *all* of invalid/expired/revoked/foreign refresh token — **cannot distinguish revoked from expired from reused**). `invalid_client` = client authentication failed; AS MAY use 401, and **MUST** use 401 with `WWW-Authenticate` if the client authenticated via the `Authorization` header (the same text appears in OAuth 2.1 draft-09/-05 snippets).
- §6: refresh request `grant_type=refresh_token`, `refresh_token` REQUIRED, `scope` OPTIONAL — requested scope MUST NOT exceed the originally granted scope (omitted ⇒ same as originally granted); RT is bound to the client it was issued to; confidential clients MUST authenticate; AS MUST validate the RT. "The authorization server MAY issue a new refresh token, in which case the client MUST discard the old refresh token" — **the MUST is on the client**; AS MAY revoke the old RT after issuing a new one; if a new RT is issued its scope MUST be identical to the presented RT's. A refresh response may carry **no** `refresh_token` (then the old one stays valid) — relevant to the classifier: absence of a new RT ≠ revoked.
- §10.4 (secondary quotation): RT confidentiality in transit/storage; TLS only; AS MUST maintain and verify the client binding; when client authentication is not possible AS SHOULD deploy other means to detect RT abuse. (RFC 9700 §4.14 V restates this.)
**Implications** — Refresh-failure signature the classifier may rely on: **HTTP 400 + `{"error":"invalid_grant"}`** (S), `invalid_client`→401 for client-auth failures. Because `invalid_grant` conflates revoked/expired/reuse/foreign-client, a tester must separately prove (a) correct client authentication, (b) token never expired by TTL/inactivity, before attributing the failure to revocation. Many providers deviate (return 401/403/`invalid_request`/200 w/ error) ⇒ treat deviations as interop notes and fall back to "no new tokens issued" as the primary signal.

### STD-009 RFC 9449 — DPoP (S, snippets only)

Observed text: proof validation includes `typ` `dpop+jwt`, asymmetric `alg`, `htm`/`htu` match, nonce match if server provided one, `iat`/nonce-timestamp within an "acceptable window", for RS use `ath` equals hash of the AT and proof key equals the AT-bound key. Servers **MAY** store `jti` per proof for the acceptance window to block replay; strict single-use "may not always be feasible" (multi-node without shared state). Servers MAY accept `iat` slightly in the future. A server-provided nonce yields freshness without trusting client clocks. An attacker controlling the client can pre-generate proofs with future `iat`. DPoP-bound ATs use `Authorization: DPoP <token>`. Public-client RT binding to the DPoP key is described as part of DPoP/RFC 9700 §4.14.2 (V) (RFC 9700 says DPoP can sender-constrain access and refresh tokens).
**Implications** — DPoP binds *who may use* a token, not *whether it is still authorized*. Revocation semantics are those of the underlying AT/RT. **Test-validity**: every post-revocation probe against a DPoP RS must carry a *fresh valid proof* (new `jti`, current `iat`, correct `htm/htu/ath`, current nonce), else a 401/400 is a proof failure, not revocation enforcement (SV-002). Server `jti` replay tracking absent ⇒ legitimate (spec-permitted) ⇒ risky-config at most.

### STD-012/013 RFC 8414 & OIDC Discovery 1.0 (V, both read in full)

**Exact metadata field names (V):**
- RFC 8414 §2 (all OPTIONAL unless stated): `issuer` (REQUIRED, https, no query/fragment), `authorization_endpoint`, `token_endpoint`, `jwks_uri`, `registration_endpoint`, `scopes_supported`, `response_types_supported` (REQUIRED), `response_modes_supported`, `grant_types_supported` (default `["authorization_code","implicit"]`), `token_endpoint_auth_methods_supported` (default `client_secret_basic`), `token_endpoint_auth_signing_alg_values_supported`, **`revocation_endpoint`**, `revocation_endpoint_auth_methods_supported` (default `client_secret_basic`), `revocation_endpoint_auth_signing_alg_values_supported`, **`introspection_endpoint`**, `introspection_endpoint_auth_methods_supported` (if omitted "determined by other means"), `introspection_endpoint_auth_signing_alg_values_supported`, `code_challenge_methods_supported` (omitted ⇒ **PKCE not supported**), `service_documentation`, `ui_locales_supported`, `op_policy_uri`, `op_tos_uri`, `signed_metadata` (JWT; if supported its values take precedence).
- Location: `/.well-known/oauth-authorization-server` **inserted between host and path of the issuer** (RFC 8414 §3); OIDC Discovery §4 instead **appends** `/.well-known/openid-configuration` to the issuer. §5 compat note: for issuers with a path, try the RFC 8414 transformation first, fall back to OIDC's. `issuer` in the document MUST equal the issuer used to fetch it (8414 §3.3; Discovery §4.3) else the data MUST NOT be used; a 200 + `application/json` is required.

### STD-014 OIDC Core 1.0 (V §1–§3.3.2; §11/§12 = S)

**ID Token (§2, V):** REQUIRED claims `iss, sub, aud, exp, iat`; `auth_time` (REQUIRED when `max_age` was requested or `auth_time` was requested as Essential; else OPTIONAL), `nonce`, `acr`, `amr`, `azp`. **`exp`: "on or after which the ID Token MUST NOT be accepted by the RP when performing authentication with the OP" — current time MUST be before `exp`; leeway MAY be "some small leeway, usually no more than a few minutes". NOTE (normative-adjacent): "The ID Token expiration time is unrelated [to] the lifetime of the authenticated session between the RP and the OP."** `sid` is not defined in Core §2 (it is defined by Front-/Back-Channel Logout, V). ID tokens MUST be signed; `alg: none` only for code flow when the client registered for it.
**Authentication Request (§3.1.2.1, V):** `prompt` is a space-delimited list: **`none`** — OP MUST NOT display any UI; MUST return an error (typically `login_required`, `interaction_required`, `consent_required`, `account_selection_required`) if the user is not already authenticated / consent absent; usable "as a method to check for existing authentication"; **`login`** — OP SHOULD re-authenticate; if it cannot MUST return an error (typically `login_required`); `consent`; `select_account`. `none` combined with any other value ⇒ error. Unknown `prompt` values: OP MAY error or ignore. **`max_age`**: allowable seconds since the last time the user was *actively* authenticated by the OP; if exceeded the OP **MUST attempt to actively re-authenticate**; ID token **MUST** then include `auth_time`; `max_age=0` ≡ `prompt=login`. **`id_token_hint`**: if the user it identifies is already (or becomes) logged in → positive response, "otherwise [OP] MUST return an error, such as `login_required`"; SHOULD be present with `prompt=none`; OP SHOULD accept ID tokens of a current/recent RP session **even when `exp` has passed** (§3.1.2.2 item 5); OP MUST NOT return tokens for a different user than the requested `sub` (§3.1.2.2 item 4).
**Error responses (§3.1.2.6 / §3.1.3.4, V):** authorization-endpoint errors go to `redirect_uri` (query for code flow; fragment for implicit/hybrid) with `error`, `error_description`, `state`; OIDC adds `interaction_required`, `login_required`, `account_selection_required`, `consent_required`, `invalid_request_uri`, `invalid_request_object`, `request(_uri)_not_supported`, `registration_not_supported`. **Token endpoint errors: HTTP 400, JSON `error`** (as RFC 6749 §5.2).
**ID Token validation (§3.1.3.7, V):** decrypt if applicable; `iss` exact match; `aud` contains client_id (reject if additional untrusted audiences); signature per `alg` (TLS may replace signature check for ID tokens received directly from the token endpoint); `exp`: current time MUST be before it; `iat` may be used to reject tokens "issued too far away from the current time" (window is client-specific); `nonce` MUST match if sent; `acr` SHOULD be checked if requested; **if `auth_time` was requested (incl. via `max_age`), client SHOULD check it and request re-authentication if too much time has elapsed**.
**Session/consent (§3.1.2.3, V):** OP MUST re-authenticate when not already authenticated or `prompt=login`; MUST NOT interact when `prompt=none`; how the OP authenticates (e.g. session cookies) "beyond the scope".
**Offline access / refresh (§11, §12 — S, secondary quotations):** `offline_access` scope requests a refresh token usable while the user is not present; the OP **must ignore the `offline_access` request** unless the response type yields an authorization code (e.g. `code`, hybrid) and consent is obtained (via `prompt=consent` or "other conditions for processing" e.g. prior administrative consent); `offline_access` does not guarantee a refresh token (OAuth 2.0 issuance is at AS discretion) and RTs may be issued without it. **§12.2 (S, via an implementation doc quoting Core):** when a refresh response includes a new ID Token its `iss` and `azp` MUST equal the original; **`auth_time` MUST represent the time of the *original* authentication, not the refresh time**; refresh ID tokens carry no `nonce` (S, third-party PR text). §12.3: refresh errors as RFC 6749 §5.2 (S).
**Not read:** §5.3.3 UserInfo error response (expectation (I): bearer-token errors per RFC 6750 §3 `invalid_token` 401), §16.18 (lifetimes of ATs and RTs), §16.9 Token Reuse, §15.5.2 nonce notes.
**Unspecified / implementation-defined:** whether the OP session is shared with the RP session; when the OP session ends (idle/absolute) — only `max_age`/`auth_time` offer a client-side probe; whether `sid` is present in ID tokens (OPTIONAL; advertised by `*_logout_session_supported`).
**Testable observations / implications** — (1) **Session liveness probe:** an authorization request with `prompt=none` (+ `id_token_hint`) returning a code (success) vs `login_required` (error, via redirect) is the standardized black-box test that the *OP session* is alive/dead after admin logout/disable. (2) **Re-auth enforcement probe:** `max_age=0`/`prompt=login` must force a login UI (a silent success where the OP must re-authenticate is a MUST violation, §3.1.2.1/§3.1.2.3 — except OP policy cannot-reauthenticate → error). (3) `auth_time` stays constant across refreshes — comparing `auth_time` of refreshed ID tokens with login time distinguishes refresh from fresh authentication. (4) ID-token `exp` says nothing about session end (explicit NOTE) — an expired ID token is *not* evidence of logout; a still-unexpired ID token is *not* evidence of a live session.

### STD-015 OIDC RP-Initiated Logout 1.0 (V, Final)
**Requirements** — RP redirects UA to `end_session_endpoint` (OP MUST support GET and POST). Params: `id_token_hint` (RECOMMENDED), `logout_hint`, `client_id`, `post_logout_redirect_uri` (MUST be pre-registered, exact match), `state`, `ui_locales`. With `id_token_hint` OP **MUST** validate it issued it; OP **SHOULD** accept ID tokens whose `exp` has passed if the RP/`sid` has a current or recent session; mismatching `sid` ⇒ treat as suspect, MAY decline. OP **SHOULD** ask the user whether to log out of the OP; **MUST** ask if no/mismatched `id_token_hint`; "yes" ⇒ OP MUST log out. OP then uses RPs' registered logout mechanism(s) (Session Mgmt / Front-Channel / Back-Channel) to notify RPs; initiating RP is included before post-logout redirect. §4: logout requests are idempotent — **not an error** to request logout when no session exists. §2: it is up to the RP whether to log out locally first; OP notifications can be unreliable. §6: unauthenticated logout is a DoS vector ⇒ OPs should confirm with user.
**Unspecified** — effect on ATs/RTs (nothing said); timing of RP notification; what "log out the End-User" does to refresh tokens (see STD-017 §2.7 for RT guidance); notification retry semantics except as in STD-017.
**Testable** — redirect chain, confirmation page presence (blocks automation without `id_token_hint`), cookie clearing (`Set-Cookie` expiry), OP session cookie validity afterwards (silent `prompt=none` auth should fail — (I) pending Core), RP back-channel hit.
**Implications** — API-level tokens surviving RP-initiated logout is *not* contradicted by this spec. A successful logout is: OP session dead (prompt=none ⇒ `login_required` — (U) Core) + RP session dead (cookie replay test). Automation needs the `id_token_hint` to avoid the mandatory confirmation.

### STD-016 OIDC Front-Channel Logout 1.0 (V, Final)
RP registers `frontchannel_logout_uri` (same domain/port/scheme as a registered redirect URI); OP renders it in an `<iframe>`; RP clears session state incl. cookies and HTML5 storage; already-logged-out ⇒ success. OP MAY add `iss`+`sid` (both or neither); RP MAY verify them against its ID token and ignore on mismatch. RP response SHOULD include `Cache-Control: no-store`. §4.1: browsers blocking third-party content/cookies can prevent the iframe from reaching RP state; spec recommends defensive detection; Back-Channel "not known to be affected".
**Unspecified** — delivery guarantee; ordering; behaviour when UA has the RP tab closed.
**Implications** — front-channel failure is a **documented limitation**, not a vulnerability. Test with a first-party-realistic browser profile and report `needs verification` when third-party-cookie blocking might explain it.

### STD-017 OIDC Back-Channel Logout 1.0 (V, Final; errata set 1)
**Requirements** — OP POSTs `application/x-www-form-urlencoded` `logout_token=<JWT>` to RP's `backchannel_logout_uri`. Logout Token claims: `iss`, `aud`, `iat`, `exp`, `jti` REQUIRED; `events` REQUIRED with member `http://schemas.openid.net/event/backchannel-logout` (value `{}`); `sub` and/or `sid` (at least one; if no `sid`, all sessions of iss+sub); **`nonce` PROHIBITED**; MUST be signed (not `none`); `typ` `logout+jwt` RECOMMENDED. OP encouraged to use short `exp` "preferably at most two minutes". RP **MUST** validate (signature, `iss/aud/iat/exp`, sub/sid present, events member, no nonce; optional jti replay check; optional session-matching checks); failure ⇒ **HTTP 400**. After a valid token the RP "clears any state associated with the identified session(s)" — mechanism "implementation specific". Success ⇒ **200** (OPs must tolerate **204**); invalid/failed ⇒ **400** (body MAY be JSON `error`, `error_description`); response SHOULD have `Cache-Control: no-store`. OP **SHOULD NOT** retransmit except for suspected recoverable failure (then SHOULD delay) — same logic as RFC 8935. **§2.7: refresh tokens issued without `offline_access` to a logged-out session SHOULD be revoked; those with `offline_access` "normally SHOULD NOT be revoked".** RP must be network-reachable from OP.
**Unspecified** — effect on access tokens; propagation time; what happens if RP is unreachable (retry limited/undefined); RP session store semantics.
**Testable** — (in the lab) emit signed logout tokens to a test RP; verify HTTP 400 on each validation failure class (missing events, nonce present, alg none, wrong aud, expired); post-logout RP session cookie replay; RT behaviour split by `offline_access`.
**Implications** — as OP-side tester you can observe the OP→RP POST only if you host the RP endpoint. As client-side tester, observe RP session death after OP-initiated logout (cookie replay) and RT status. Surviving `offline_access` RT after logout is **explicitly expected**.

### STD-022 OpenID Shared Signals Framework 1.0 (V to §8.1.4; Final)
**Status** — document dated 29 Aug 2025 with `spec_version` value `"1_0"` for Final; OIDF membership approved it as a Final Specification together with CAEP and RISC (announcement snippet (S): 85 approve, 1 object, 25 abstain). Absent `spec_version` ⇒ assume `1_0-ID1` (V).

**Management API (V; OPTIONAL overall, RECOMMENDED: status + verification)** — Configuration endpoint: POST create (201; 409 if multiple streams unsupported), GET (with/without `stream_id`; list or single; `[]` when none), PATCH (partial; 200/202), PUT (replace; missing receiver-supplied props deleted), DELETE (204). Default delivery if omitted = poll (`urn:ietf:rfc:8936`). Status endpoint: values `enabled` (Transmitter MUST transmit), `paused` (MUST NOT transmit; SHOULD hold and later send; MAY drop; MUST preserve ordering per subject or send only non-superseded), `disabled` (MUST NOT transmit; nothing held). Transmitter-initiated status change ⇒ MUST send Stream Updated event. Add/Remove subject: POST; add → 200 (may silently ignore), remove → 204; 404 for unknown stream or (optionally silent) unknown subject; 429 rate limiting. **Testable** — discovery doc validity; stream CRUD codes; status transitions; verification round-trip latency (a clean baseline for transport delay *excluding* receiver enforcement); `iss` equality checks.
**Implications** — before attributing slow enforcement to a receiver, **measure the stream's own baseline** via Verification events; absence of any mandated receiver behaviour means "event delivered, access continues" is a *product/enforcement* finding classified by documented behaviour, never by SSF alone.

### STD-026 RFC 6455 WebSocket (S — snippets; full text not read)

- **Authentication (S, secondary quotation of RFC 6455 §10.5 via the `websockets` project docs):** the protocol "doesn't prescribe any particular way that servers can authenticate clients during the WebSocket handshake"; the server "can use any client authentication mechanism available to a generic HTTP server, such as cookies, HTTP authentication, or TLS authentication". **No re-authentication mechanism exists in the protocol after the handshake** (inferred from the absence of any such text in the snippets (I) — to be confirmed by reading §1.6/§10 and §7.4).
- **Handshake (S, primary snippet):** client sends HTTP/1.1 `GET` with `Upgrade: websocket`, `Connection: Upgrade`, `Sec-WebSocket-Key`, **`Origin`** (browser clients), `Sec-WebSocket-Version: 13`; the server "can also set cookie-related option fields". If the server rejects the handshake it returns an HTTP error (e.g., 400 per §4.2.1, "an appropriate error code"; 401/403 are therefore possible HTTP responses *before* the upgrade; 101 on success). Security model is "origin-based" (abstract).
- **Close codes (S):** `1008` = "Policy Violation" (RFC 6455 §7.4.1; sent when a message violates server policy — snippets give examples incl. unauthorized/failed authentication after handshake); `1000` normal, `1001` going away, `1002` protocol error, `1006` abnormal (never sent on the wire — set locally), `1011` internal error. **`4000–4999` are reserved for private/application use (U, from memory of §7.4.2 — verify)**; many apps use 4401/4403-style codes for auth failures — implementation-defined.
- **Primary-source example of credential expiry on a WebSocket (S, RFC 8887 / JMAP-over-WebSocket, STD-034):** credentials used for the handshake "remain in effect for the duration of the WebSocket connection"; if the user's credentials expire "the server can either treat subsequent requests as if they are unauthenticated or close the WebSocket connection", and in the latter case "MAY send a Close frame with a status code of 1008". This is a *subprotocol-specific* statement and shows that both behaviours are standards-acceptable.
- **ASVS 5.0.0 (V via Cornucopia): V4.4.1 WSS for all WebSocket connections (L1); V4.4.2 check the `Origin` header during the handshake against an allowlist (L2); V4.4.3 if standard session management cannot be used, dedicated tokens complying with Session Management requirements (L2); V4.4.4 dedicated WebSocket session tokens obtained/validated through the previously authenticated HTTPS session (L2).**
**Implementation-defined** — whether an established connection is terminated on token/session revocation; per-message re-validation; idle/ping policy; close code used.
**Testable** — keep an authenticated WebSocket open across the revocation event; send/receive probes at intervals; observe: server Close frame (code/reason), TCP close (1006), continued message acceptance, per-message error frames (app-level). Handshake with a revoked token ⇒ HTTP 401/403 (not 101).
**Implications** — an open WebSocket that keeps working after revocation is **not a protocol violation** (no verified text requires otherwise); classify as `NEEDS_VERIFICATION`/`RISKY_CONFIG` with the measured connection lifetime, upgraded only by ASVS V7.4.1 ("disallows any further use of the session") when the target's policy profile includes ASVS and the WebSocket rides the application session.

### STD-027/035 RFC 9110 §6.6.1 `Date`, RFC 9111 `Age` (S)

- **`Date` (S, quotations of RFC 9110 §6.6.1 in third-party issue trackers):** an origin server **with a clock MUST generate `Date` in all 2xx, 3xx and 4xx responses**, MAY in 1xx and 5xx; a recipient with a clock that receives a response lacking `Date` MUST record the receive time and append a `Date` if it caches/forwards. (RFC 7231 §7.1.1.2 mirror: an origin server **MUST NOT** send `Date` if it has no clock providing a reasonable approximation of UTC; "the date ought to represent the moment just before the payload is generated … can be generated at any time during message origination".) Format is IMF-fixdate (`Sun, 06 Nov 1994 08:49:37 GMT`) ⇒ **resolution is 1 second** (sub-second digits cannot be expressed); recipients must also accept the two obsolete formats. 5xx responses (the usual failure mode of gateways) may lack `Date`.
- **`Age` (V-snippet, httpwg RFC 9111 §5.1):** "conveys the sender's estimate of the time since the response was generated or successfully validated at the origin server"; non-negative integer seconds; computed per §4.2.3 (which uses `Date`). A response with `Age > 0` came from a cache, so its `Date` is the *origin* generation time and is **older than the moment the client received it** — such a response must not be used as a fresh clock sample and, more importantly, **must not be used as evidence of current authorization state** (cache served it).
- **Clock alignment consequences for RevocationGap (I):** (a) offset estimate = (`Date` header − midpoint of request/response local times); uncertainty ≥ ±0.5 s from 1 s truncation plus RTT/2; take the median/min-RTT sample over many requests; (b) ignore responses with `Age > 0`, 3xx/5xx samples, and responses lacking `Date`; (c) never compare `exp` (second resolution, NumericDate may carry fractions) against a sub-second tester clock without the skew band (SV-010); (d) if RS `Date` and AS `Date` differ by more than the band, record both offsets (AS and RS clocks can differ from each other and from the tester).
**Unspecified** — accuracy of server clocks; synchronization source; behaviour of CDNs/gateways that rewrite or cache `Date`.

### STD-028 RFC 6265bis (U — still not read in pass 2; ASVS cookie facts added below)
Not read. From V sources only: RFC 6750 §5.2/5.3 — bearer tokens MUST NOT be stored in cookies that can be sent in the clear; cookie-stored bearer tokens must take CSRF precautions; Front-Channel §2 — RP logout clears cookies/HTML5 storage; Clear-Site-Data guidance from OWASP (S). **To verify:** `Max-Age`/`Expires` precedence; session cookie deletion via `Set-Cookie` with past `Expires`; cookies' independence from server-side session state (a deleted cookie ≠ server-side invalidation).

### STD-029 OWASP ASVS 5.0.0 (V — verbatim requirement text via OWASP Cornucopia taxonomy pages that reproduce ASVS 5.0.0)

ASVS is a *verification standard for application security*, not a protocol standard: a failure is a **vulnerability in the assessed application against the ASVS level the owner claims/targets**, which is policy-profile dependent (SV-050). Requirement text below is paraphrase of the verbatim wording read; levels are those shown on the pages.
- **V7.4.1 (L1, L2, L3):** when session termination is triggered (logout or expiration) the application **disallows any further use of the session**. For reference tokens/stateful sessions this means invalidating session data at the backend. "**Applications using self-contained tokens will need a solution such as maintaining a list of terminated tokens, disallowing tokens produced before a per-user date and time or rotating a per-user signing key.**"
- **V7.4.2 (L1–L3):** the application terminates **all active sessions when a user account is disabled or deleted** (e.g., an employee leaving).
- **V7.4.3 (L2, L3):** application gives the *option* to terminate all other active sessions after change/removal of any authentication factor (password change via reset/recovery, MFA settings update). V7.4.4 (L2) logout visible on all authenticated pages. **V7.4.5 (L2):** administrators can terminate sessions for an individual user or all users.
- V7.3.1/V7.3.2 (L2): inactivity timeout and absolute maximum session lifetime enforce re-authentication per documented risk decisions. V7.1.1 (L2): the documentation states inactivity and absolute lifetimes. V7.5.2 (L2): users can view and (after re-authenticating with ≥1 factor) terminate any/all sessions (secondary quote). **V7.6.1 (L2):** session lifetime and termination between relying parties and IdPs behave as documented (title-level only read).
- **V10.4.2 (L1–3):** auth code single-use; on a second valid use the AS rejects and **revokes any tokens issued** from that code. **V10.4.5 (L1–3):** AS mitigates refresh-token replay for public clients — preferably sender-constrained (DPoP/mTLS), for L1/L2 rotation is allowed, and **with rotation the AS must invalidate the RT after use and revoke *all* RTs for that authorization if an already-used RT is presented.** **V10.4.8 (L2/3):** refresh tokens have an **absolute** expiration even with sliding expiry. **V10.4.9 (L2/3):** RTs and reference ATs can be revoked by an authorized user via the AS user interface. V10.4.10 (L2/3): confidential clients authenticate on token, PAR and **token revocation** requests. V10.4.14 (L3): only sender-constrained ATs.
- **V10.5.5 (L2/3):** with OIDC back-channel logout the RP mitigates forced-logout DoS and cross-JWT confusion: logout token typed `logout+jwt`, contains the `events` claim with the correct member name, contains **no `nonce`**; short expiry (e.g., 2 min) recommended. (RP side — consistent with STD-017.)
- **V4.4.x WebSocket** — see STD-026. V3.3.x cookie attributes (title level only: `SameSite`, `__Host-` prefix, attribute rules). V9.2.2/V9.2.3 (self-contained tokens: validate token type/intended audience — title level only).
- **Intro text (S, asvs.dev):** session termination "should result in requiring re-authentication and be effective across the application, federated login (if present), and any relying parties"; for stateful mechanisms terminate by invalidating the session on the backend; when an SSO provider handles sessions, scoping decisions apply.
**Implications** — **This supersedes my first-pass claim that JWT survival after logout is simply "expected".** At protocol level (RFC 9068/7009) a JWT AT is valid until `exp`; **at ASVS 5.0.0 level, V7.4.1 (L1) requires that terminated sessions/self-contained tokens stop working**, and V7.4.2 (L1) that disabling/deleting an account terminates all sessions. Hence "JWT/session still works after logout/disable" is `EXPECTED` w.r.t. OAuth/OIDC specs but `VULN`/`RISKY_CONFIG` w.r.t. an ASVS-L1+ profile for the *application's own session tokens* (not for third-party-issued API ATs the app merely relies on). Password change: only the *option* to terminate other sessions is required (V7.4.3, L2); not automatic termination.

### STD-030 OWASP Session Management Cheat Sheet (S)
Snippets: logout must invalidate the session **at least server-side**; browser-close events cannot enforce logout — use server-side idle and absolute timeouts + explicit logout; `Clear-Site-Data: "cache","cookies","storage"` on logout; use `Cache-Control: no-store` on sensitive pages. **Implications:** client-side cookie deletion alone is not logout; replaying the old cookie is the correct black-box probe.

### STD-031 NIST SP 800-63B-4 (S — numbers from pages.nist.gov / nvlpubs PDF search snippets); 63C-4 (U)

- **800-63B-4 reauthentication (S):** at **AAL2** "periodic reauthentication of subscriber sessions SHALL be performed (Sec. 5.2)"; "a definite reauthentication overall timeout **SHALL** be established, which **SHOULD be no more than 24 hours** at AAL2"; **inactivity timeout SHOULD be no more than 1 hour**; after an inactivity timeout (but before the overall timeout) the verifier MAY allow reauthentication with only a password or biometric comparison plus the session secret. (AAL1 values and §5 session-management requirements on termination/logout were not in the snippets — **U**.) - **800-63C-4 (federation) — NOT read (U):** no statements about RP session termination, assertion lifetimes or IdP-RP logout propagation are made here.
**Implications** — numeric reauthentication limits are *policy inputs* for tests of "session lifetime ≤ X" (RevocationGap policy profile `nist-aal2` / `nist-aal3`, SV-050); they are SHALL/SHOULD at federal-system-assurance level, not protocol rules. ## 4. Standards-derived test-validity rules (for the outcome classifier)

Format: **SV-id**: rule → classifier consequence. Class names follow the project taxonomy: `EXPECTED` (expected protocol semantics), `DOC_DELAY` (documented enforcement delay), `RISKY_CONFIG`, `VULN` (real vulnerability), `NEEDS_VERIFICATION`, `INCONCLUSIVE`. "Provider doc" means vendor documentation verified by other agents; standards alone never upgrade to `DOC_DELAY`.

**Probe validity & controls**
- **SV-001** Every revocation experiment needs a **positive control** (token works before the change) and a **negative control** (garbage/foreign token of same shape is rejected) on the same endpoint; without them classify `INCONCLUSIVE`. (I; grounded in 7009 §2.2: garbage tokens look "successful" at the revocation endpoint.)
- **SV-002** The post-change probe must differ from the pre-change probe **only** in token/session state: same method, URL, headers, body, scopes, client, DPoP key. A 401/400 caused by a stale DPoP proof, TLS client cert, `iat` window, or `htu` mismatch is **not** enforcement evidence (9449 (S)): `INCONCLUSIVE`. For DPoP RS, mint a fresh proof (new `jti`, current `iat`, `ath`, nonce if challenged) per probe.
- **SV-003** Use the correct credential-presentation method: `Authorization: Bearer` (preferred), body param only for form posts, query param never by default (6750 §2; 9700 §4.3.2). A rejection of query-param tokens is not revocation.
- **SV-004** Do not conclude from a single post-change success. 7009 §2.1 acknowledges "propagation delay"; poll until the first rejection and until stability (N consecutive rejections), or timeout; report `t_first_reject`, `t_stable_reject`, polling interval, and the number of attempts. Time zero is the instant the AS acknowledged the change (e.g., revocation 200 / admin API 2xx) using server-aligned clock, not tester wall clock.
- **SV-005** Revocation/logout endpoint success codes are not state proofs: 7009 returns **200 for invalid tokens** (§2.2); back-channel `200` and OIDC logout redirects only say the request was processed. Always verify state with an independent oracle (introspection, RS probe, refresh attempt, `prompt=none`).
- **SV-006** HTTP **503** from a revocation endpoint ⇒ the token **still exists** (7009 §2.2.1); mark the revoke step failed and `INCONCLUSIVE` for downstream rejection tests.
- **SV-007** The revoking client must be the token's client; an error revoking a token issued to another client is expected (7009 §2.1) — setup failure, not a finding.
- **SV-008** Introspection 401 (bad RS credentials) is a tester-config error (7662 §2.3): `INCONCLUSIVE`. Inactive tokens return **200 `{"active":false}`**; a 4xx for an inactive token is a deviation (MUST, 7662 §2.2/2.3) → `VULN`-low/`NEEDS_VERIFICATION` (interop defect, not an access flaw).
- **SV-009** Interpret RS rejection by signal: 401 + `WWW-Authenticate: Bearer error="invalid_token"` ⇒ credential rejected (6750 §3.1); 403 `insufficient_scope` ⇒ authenticated but unauthorized (relevant to *role removal*); 400 `invalid_request` ⇒ malformed (probe bug); a 403/404 for a revoked token without `WWW-Authenticate` is a deviation from SHOULD, `NEEDS_VERIFICATION` about *why*, not "still valid".

**Time & expiry**
- **SV-010** Token accepted at or after `exp` by more than the skew tolerance ⇒ `VULN` (MUST: 7519 §4.1.4, 9068 §4). **Skew bands are RevocationGap policy defaults, NOT spec numbers, and are user-configurable (`skew_tolerance_s`, `skew_ambiguous_s`).** The specs (RFC 7519 §4.1.4, RFC 9068 §4, OIDC Core §2) say only: the current time MUST be before `exp`, and implementers MAY allow "some small leeway, usually no more than a few minutes". Proposed defaults: acceptance within `skew_tolerance_s` = 60 s of `exp` ⇒ `EXPECTED`; between 60 s and `skew_ambiguous_s` = 300 s ⇒ `NEEDS_VERIFICATION` (leeway-ambiguous); beyond 300 s ⇒ `VULN`. The measurement floor is ≥1 s because `Date` has 1-second resolution (STD-027): never classify on differences < ~2 s. Estimate offset from RS `Date` per STD-027/035 (ignore `Age>0`, 5xx, missing `Date`) and from the AS token response (`expires_in`).
- **SV-011** Token rejected before `exp` after a revocation/disable/role change: `EXPECTED` positive enforcement. Record `time_saved = exp − t_reject`.
- **SV-012** JWT AT still accepted before `exp` after revocation/disable/role-removal/password-change: **not a violation** (9068 §4 has no revocation step; 7009 §3). Default class `EXPECTED`; upgrade to `RISKY_CONFIG` when `remaining_ttl > 3600 s` (6750 §5.3 SHOULD ≤ 1 h); to `DOC_DELAY` only if provider docs state the delay; to `VULN` only if provider docs/contract promise immediate enforcement (e.g., introspection-based RS) or the same RS rejects the token via another path (inconsistent enforcement). **ASVS caveat (second pass, STD-029): under a policy profile that includes ASVS 5.0.0 L1+, V7.4.1 requires the application to disallow further use of terminated *self-contained tokens/sessions* (logout/expiry) and V7.4.2 to terminate all sessions on account disable/delete — then continued acceptance of the app's own session JWT after logout or disable is `VULN` (profile-dependent), even though it is protocol-`EXPECTED` for OAuth access tokens. The classifier must record which profile produced the label.**
- **SV-013** AT lifetime > 1 h ⇒ informational `RISKY_CONFIG` (6750 §5.3 SHOULD; not MUST).
- **SV-014** `nbf`, `iat`, `jti` are OPTIONAL at base level (7519 §4.1); RS ignoring `jti` replay is `EXPECTED`; absence of `jti` in an AT claimed as RFC 9068 ⇒ profile non-conformance (9068 §2.2 REQUIRED) → informational.

**Opaque tokens / introspection**
- **SV-015** Opaque AT whose AS supports AT revocation (revocation returned 200 and not `unsupported_token_type`), RS validates via introspection, and introspection reports `active:true` after the revoke beyond the propagation window ⇒ `VULN` candidate (7662 §4 MUST check revocation; 7009 "invalidation takes place immediately"). Window threshold not standardized — use measured convergence and provider doc; default threshold e.g. > 30 s ⇒ `NEEDS_VERIFICATION`, persistent beyond configured max ⇒ `VULN`.
- **SV-016** AS reports `active:false` but RS still accepts ⇒ RS-side caching or local validation. If acceptance stops at a constant offset after change (step) ⇒ cache TTL; compare with RS documentation; 7662 allows caching (MAY) but forbids caching beyond `exp` — acceptance after `exp` ⇒ `VULN` (SV-010). Otherwise `RISKY_CONFIG`/`DOC_DELAY`.
- **SV-017** Inactive-token introspection responses containing extra members (reasons, scopes) ⇒ informational leak (SHOULD NOT, 7662 §2.2/§4).

**Revocation endpoint capability**
- **SV-018** `unsupported_token_type` for an AT ⇒ `EXPECTED` (AT revocation is SHOULD; 7009 §2); record capability `at_revocation=false` and re-classify all "AT survives revocation" outcomes as `EXPECTED`/`RISKY_CONFIG`, never `VULN`.
- **SV-019** RT revoked (200) then refresh still succeeds ⇒ `VULN` (MUST support RT revocation, 7009 §2) — after confirming it is the same client, same grant, no rotation successor presented, and no 5xx/503 at revoke. Expected failure signature: HTTP 400 `{"error":"invalid_grant"}` (RFC 6749 §5.2 via quotations — S; same text in OAuth 2.1 drafts). `invalid_grant` is returned for invalid, expired, revoked, foreign-client **and** reused tokens — so first rule out TTL/inactivity expiry (check issuance time vs RT lifetime/ASVS V10.4.8 absolute expiry) and client mismatch; an `invalid_client`/401 is a client-authentication problem (`INCONCLUSIVE`). A refresh response *without* a new `refresh_token` means the old RT remains in force (RFC 6749 §6) — not revocation.
- **SV-020** RT revoked, previously issued AT still valid: `EXPECTED` if `at_revocation=false`; if AS supports AT revocation, SHOULD-level deviation (7009 §2.1) ⇒ `NEEDS_VERIFICATION`/`RISKY_CONFIG`.
- **SV-021** AT revoked, RT still valid ⇒ `EXPECTED` (MAY cascade, 7009 §2.1).

**Refresh-token rotation**
- **SV-022** Public client (no client auth), RT not sender-constrained, rotation advertised or observed: re-presenting an already-rotated RT and getting new tokens ⇒ `VULN` (9700 §2.2.2/§4.14.2 MUST). Confidential client ⇒ `EXPECTED` (rotation optional) unless provider promises rotation.
- **SV-023** After reuse of an old RT, the AS "will revoke the active refresh token" (9700 §4.14.2): if the newest RT continues to work, `NEEDS_VERIFICATION` (descriptive text; AS cannot know which party replayed). A short concurrency grace window is not addressed by the spec — treat sub-second/few-second windows as `EXPECTED` unless documented otherwise (I).
- **SV-024** RT survives password change / admin logout ⇒ permitted (9700 "MAY revoke"). `EXPECTED` by standards; use provider docs and ASVS (S) to upgrade to `RISKY_CONFIG`.

**Logout (OIDC)**
- **SV-025** Back-channel: OP-side — logout request → RP endpoint must respond 200 (or 204) on valid, 400 on invalid tokens (017 §2.6/2.8). RP returns 200 but the identified RP session remains usable ⇒ `VULN` candidate (RP "clears any state ... session(s)", 017 §2.7) → `NEEDS_VERIFICATION` if session identification (sid vs sub) mismatch is possible.
- **SV-026** Back-channel Logout Token validity matrix to test the RP: missing `events`, `nonce` present, `alg:none`, missing `sub`+`sid`, wrong `aud`/`iss`, expired — each MUST yield 400 (017 §2.6). Accepting any of them ⇒ `VULN` (RP).
- **SV-027** Refresh tokens: non-`offline_access` RT surviving back-channel logout ⇒ SHOULD deviation → `NEEDS_VERIFICATION`; `offline_access` RT surviving ⇒ `EXPECTED` (017 §2.7). Determining `offline_access` requires the granted scope (token response `scope`) — if unknown ⇒ `INCONCLUSIVE`.
- **SV-028** Front-channel logout non-effect ⇒ cannot be classified `VULN` unless a first-party/non-third-party-blocked context was used (016 §4.1) → `NEEDS_VERIFICATION`.
- **SV-029** RP-initiated logout: repeated/idempotent logout requests succeeding is `EXPECTED` (015 §4); missing `id_token_hint` ⇒ OP MUST ask the user (015 §2) so an unattended confirmation page is `EXPECTED`, `INCONCLUSIVE` for the logout outcome; expired `id_token_hint` accepted is `EXPECTED` (SHOULD accept).
- **SV-030** API tokens (AT/RT) unaffected by RP-initiated or back-channel logout ⇒ `EXPECTED` (no verified spec requires it; only RT SHOULD as per SV-027). Do not report as defect on standards grounds alone.
- **SV-031** ID token accepted by an RS as an access token, where RS claims RFC 9068 profile ⇒ `VULN` (typ `at+jwt` check MUST, 9068 §4); otherwise `RISKY_CONFIG` (token confusion).

**Sessions (cookie/stateful)**
- **SV-032** Server-side session cookie replayed after explicit logout is still accepted ⇒ `VULN` **under an ASVS 5.0.0 profile (V7.4.1, L1–L3, V)**, and per the OWASP cheat sheet (S: invalidate server-side). Client-side cookie deletion alone is not logout; cookie attributes (`Max-Age`/`Expires`) say nothing about server-side validity (see STD-028 note).
- **SV-033** After user disable/delete, existing sessions/tokens (own sessions) still valid ⇒ `VULN` under an ASVS 5.0.0 profile (**V7.4.2, L1–L3, V**); with no ASVS profile, `RISKY_CONFIG` (no OAuth/OIDC text requires it). Report the time-to-convergence; sessions of *third-party* IdPs are covered by V7.6.1 (documented behaviour) — `NEEDS_VERIFICATION`.
- **SV-034** After password change, other sessions remain valid ⇒ ASVS 5.0.0 **V7.4.3 (L2, V)** requires only that the application *gives the option* to terminate other sessions; automatic termination is not required ⇒ `EXPECTED`/`RISKY_CONFIG` (not `VULN`) unless the target documents automatic termination. RFC 9700 §4.14.2: AS MAY revoke RTs on password change.

**Sender-constrained tokens**
- **SV-035** Bound AT presented without a valid proof/cert ⇒ must be rejected (9449 (S), 9700 §4.10.1 V); acceptance ⇒ `VULN`/misconfiguration (binding not enforced). This is a *binding* test, separate from revocation tests.
- **SV-036** DPoP proof replay (same `jti`) accepted within the window ⇒ `RISKY_CONFIG` at most (tracking is optional, 9449 (S)).

**SSF / CAEP / RISC**
- **SV-037** CAEP/RISC event delivered (Receiver ack) but access continues ⇒ not a violation of SSF/CAEP (no mandated receiver behaviour; SSF §4.1.5, CAEP full text). Class by Receiver's documented/configured enforcement: documented ⇒ `DOC_DELAY`/`VULN` (if delay exceeds doc); undocumented ⇒ `NEEDS_VERIFICATION`.
- **SV-038** Before measuring end-to-end CAEP latency, establish the stream's transport baseline: `status` must be `enabled` (paused/disabled ⇒ Transmitter MUST NOT transmit — absence of events is expected); fire a Verification event (204 on request only means accepted; delivery async; receivers MUST NOT rely on sync, SSF §8.1.4). Otherwise `INCONCLUSIVE`.
- **SV-039** Transmitter conformance probes (SET profile): `exp` present ⇒ non-conformant (MUST NOT); `sub` present ⇒ non-conformant; `typ` ≠ `secevent+jwt` ⇒ non-conformant; `iss` ≠ stream/metadata `iss` ⇒ Receiver MUST reject (SSF §4.1.6). These are interop findings, not access findings.
- **SV-040** `event_timestamp` is the time the *underlying change* occurred (CAEP per-event text) and is OPTIONAL; compute delivery latency as receive-time − `event_timestamp` only when present; else use `iat` with the caveat that `iat` is SET creation time.
- **SV-041** Transmitter discovery: `GET /.well-known/ssf-configuration[/path]` (RISC legacy `/.well-known/risc-configuration`); returned `issuer` must equal the URL base (MUST) — mismatch ⇒ abort stream setup (SSF §7.2.4).
- **SV-042** Back-channel Logout Token (`exp` REQUIRED, `typ` `logout+jwt`, `nonce` prohibited) and SSF SET (`exp` MUST NOT, `typ` `secevent+jwt`) are different profiles; classifier must not apply one's validation rules to the other.

**Misc**
- **SV-043** Rate limits (429, SSF; 7009 DoS note) or `Retry-After` during probing ⇒ pause and mark window `INCONCLUSIVE`; do not count as rejection due to revocation.
- **SV-044** Metadata booleans default false when absent (`*_logout_supported`, `*_session_supported`, 016/017); absent `revocation_endpoint`/`end_session_endpoint` ⇒ capability absent ⇒ related tests `NOT_APPLICABLE`/`EXPECTED`, not findings. (Metadata names verified in RFC 8414 §2 — see STD-012; `end_session_endpoint` is from RP-Initiated Logout, not Discovery/8414.)
- **SV-045** Access control of the *tester's* own oracle: the tester needs introspection/revocation credentials authorized by the AS; if unavailable, use black-box RS probing only and downgrade claims about AS state to `INCONCLUSIVE`.

**Second-pass additions (SV-046 …; IDs appended, earlier IDs unchanged)**
- **SV-046** *Policy profiles.* Every classification records `profile` ∈ {`protocol` (RFCs/OIDF specs only), `asvs-5.0.0-L1|L2|L3`, `nist-aal2|aal3`, `vendor-doc:<provider>`}. Standards-only (`protocol`) can yield `EXPECTED`, `NEEDS_VERIFICATION`, `INCONCLUSIVE` or a MUST-violation `VULN`; ASVS/NIST/vendor profiles may yield profile-scoped `VULN`/`RISKY_CONFIG`. Default profile: `protocol`. (Resolves the tension in STD-029 vs STD-007.)
- **SV-047** *Skew bands are policy.* `skew_tolerance_s` (default 60) and `skew_ambiguous_s` (default 300) are configurable RevocationGap defaults chosen from RFC 7519's "a few minutes"; reports must print the values used. Because `Date` has 1 s resolution, never emit a timing verdict from a single sample or on differences < 2 s (STD-027).
- **SV-048** *Clock samples.* Use `Date` only from 2xx/3xx/4xx responses with no `Age` header (or `Age: 0`); discard 5xx and missing-`Date` responses (RFC 9110 §6.6.1: 5xx MAY lack it; cached responses carry `Age`, RFC 9111 §5.1). A response served from a cache (positive `Age`) must not count as "RS still accepts the token" either — mark `INCONCLUSIVE` (cache poisoned the observation); send `Cache-Control: no-cache`/unique query params only when allowed by the target's rules of engagement.
- **SV-049** *Refresh failure signature.* Treat HTTP 400 + `invalid_grant` as "refresh rejected"; HTTP 401 / `invalid_client` as client-auth failure (`INCONCLUSIVE`); any 2xx with a new `access_token` as "refresh accepted"; 2xx with an `access_token` but no `refresh_token` ⇒ old RT remains valid (RFC 6749 §6). Providers that return other codes for revoked RTs are logged as interop deviations with the raw response preserved.
- **SV-050** *OIDC session-liveness probe.* After an admin/user logout at the OP, an authorization request with `prompt=none` (+ valid `id_token_hint`) MUST NOT show UI (Core §3.1.2.1); a *success* response (code) means the OP session (or silent-auth cookie) is still alive ⇒ evidence of incomplete logout; an `error=login_required|interaction_required|consent_required|account_selection_required` redirect means dead. Use `response_mode` that keeps errors observable; error is returned via redirect to the registered `redirect_uri`.
- **SV-051** *Re-authentication enforcement.* An authorization request with `prompt=login` or `max_age=0` that is satisfied **without** an interactive login (and without error) ⇒ OP violated a MUST/SHOULD (`max_age` → MUST attempt active re-authentication; `prompt=login` → SHOULD, MUST error if it cannot reauthenticate) (Core §3.1.2.1/§3.1.2.3). The returned ID token **MUST** contain `auth_time` when `max_age` was sent; missing ⇒ `VULN`-low (interop). The RP SHOULD verify `auth_time` (Core §3.1.3.7 item 13).
- **SV-052** *ID-token expiry vs session.* Never infer session end from ID-token `exp` (Core §2 NOTE). Never treat an expired ID token as evidence of logout; never treat an unexpired ID token as evidence of a live session; use SV-050 instead. `id_token_hint` with expired ID token is accepted by OPs (SHOULD) ⇒ not a finding.
- **SV-053** *`auth_time` on refresh.* A refreshed ID token whose `auth_time` equals the *refresh* time (rather than original authentication) violates Core §12.2 (S) and can mask session age ⇒ `NEEDS_VERIFICATION`; use `auth_time` to distinguish "refresh" from "new authentication" (also RFC 9068 §2.2.1: `auth_time/acr/amr` stay the same across refreshes).
- **SV-054** *Discovery capability handling.* Read `revocation_endpoint`, `introspection_endpoint`, `end_session_endpoint`, `backchannel_logout_supported`, `backchannel_logout_session_supported`, `frontchannel_logout_supported`, `frontchannel_logout_session_supported`, `jwks_uri`, `code_challenge_methods_supported`, `grant_types_supported` from `/.well-known/openid-configuration` and/or `/.well-known/oauth-authorization-server` (issuer-with-path: try the RFC 8414 insertion form first, then the OIDC append form). The returned `issuer` MUST equal the issuer used (else abort — MUST NOT use). Missing logout booleans ⇒ false; missing `revocation_endpoint`/`introspection_endpoint` ⇒ `capability_unadvertised` (not a defect); `code_challenge_methods_supported` absent ⇒ PKCE unsupported (RFC 8414).
- **SV-055** *WebSocket probes.* (a) Handshake with a revoked token must yield an HTTP error (401/403, not 101) — if 101 ⇒ revoked token accepted at handshake (`VULN` per the same rules as HTTP: SV-012/015 by token type). (b) An **already-open** connection surviving revocation ⇒ not a standards violation (RFC 6455 has no re-auth; RFC 8887 allows either); record `connection_age_after_revocation`, last accepted message time, close code if any (1008 policy violation, 1000/1001 normal, 1006 abnormal, 4xxx app-defined), then classify via profile (ASVS V7.4.1). (c) Verify `Origin` handling separately (ASVS V4.4.2, L2) — it is not a revocation finding.
- **SV-056** *Back-channel logout RP checks (ASVS V10.5.5).* RP-side test vectors: logout token without `typ=logout+jwt` (RECOMMENDED only — accepting it is `RISKY_CONFIG`, not `VULN`, per STD-017 §4.1), with `nonce` present (MUST reject), missing `events` member (MUST reject), `exp` > ~2 min in the future (OP SHOULD NOT; RP acceptance of long-lived tokens ⇒ `RISKY_CONFIG`).
- **SV-057** *Refresh-token rotation, ASVS profile.* Under ASVS 5.0.0 V10.4.5 (L1+): presenting an already-used RT must be rejected **and all RTs for that authorization revoked** (verify with the newest RT afterwards); under `protocol` profile only SV-022/SV-023 apply. V10.4.8 (L2): RTs have an absolute expiry even with sliding expiry — probe by checking RT age against documented absolute lifetime (needs vendor doc). V10.4.2: second use of an authorization code must be rejected and previously issued tokens revoked (RFC 6749 §4.1.2 SHOULD revoke; ASVS makes it a requirement).
- **SV-058** *Reauthentication-lifetime tests (NIST profile).* With profile `nist-aal2`: overall session/reauth timeout should be ≤ 24 h (SHOULD; a timeout must exist — SHALL) and inactivity ≤ 1 h (SHOULD); `nist-aal3`: overall ≤ 12 h (SHALL), inactivity ≤ 15 min (SHOULD) (800-63B-4, S). Findings from the NIST profile are `RISKY_CONFIG` for SHOULD-level breaches and `VULN` (profile-scoped) for SHALL-level breaches; require vendor-documented or observed session lifetimes; do not apply without the profile being selected.

## 5. Ambiguities and tensions between specs

1. **"Immediately" vs "propagation delay" (RFC 7009 §2.1).** The same paragraph says invalidation is immediate and acknowledges non-zero propagation; no number. ⇒ classifier needs configured thresholds + provider docs.
2. **SHOULD cascade vs MAY cascade (7009).** RT→ATs is SHOULD (conditioned on AT-revocation support), AT→RT is MAY; the "supports AT revocation" capability is observable only indirectly (`unsupported_token_type`).
3. **7009 vs RFC 9068 on AT revocation.** 7009 expects revoked ATs to become unusable; 9068 §4 validation never checks revocation. Both can be satisfied simultaneously only if RS uses introspection or an out-of-band channel ("non-standardized", 7009 §3). Hence JWT-AT survival is ambiguous by design.
4. **RFC 7662 "active" is AS-defined** yet §4 lists MUST checks "if applicable" — which checks apply is itself AS-determined; user-disabled/role-removed handling is open.
5. **Leeway:** RFC 7519 "a few minutes" vs. DPoP freshness windows measured in seconds (9449 (S)) vs. Back-Channel "preferably at most two minutes" expiry (017 §4) — no common clock-skew number.
6. **Logout vs refresh tokens:** RFC 9700 §4.14.2 "MAY revoke RTs on logout/password change" vs Back-Channel §2.7 "SHOULD revoke non-`offline_access` RTs / SHOULD NOT revoke `offline_access` RTs". Different strengths, different scopes (AS vs RP-notified OP session). OIDC Core `offline_access` text not read (U).
7. **Logout reach:** ASVS 5.0.0 intro (S) states termination should be "effective across the application, federated login ... and any relying parties" — stronger than OIDC logout specs, which are best-effort (016 §4.1, 015 §2 "unreliable") and silent on API tokens.
8. **CAEP/SSF vs ASVS/NIST expectation of enforcement.** CAEP/SSF define signals only; enforcement is deployment-defined (SSF §4.1.5). "Continuous access evaluation" claims by vendors cannot be validated against the spec text alone.
9. **Logout Token vs SET.** Back-Channel (017 §2.4) says Logout Token is "compatible with" SET but with a more specific `typ`; it requires `exp` and `typ logout+jwt`, SSF forbids `exp` and requires `typ secevent+jwt`. Same envelope idea, incompatible profiles.
10. **RP-initiated logout confirmation (015 §2)** vs automation: OP MUST ask user absent a matching `id_token_hint`; yet 015 §6 also says unauthenticated logout is a DoS vector. Test harness must always supply `id_token_hint` (and the correct `client_id`).
11. **Status labels:** SSF/CAEP/RISC "Final" is based on an OIDF announcement snippet plus document date 29 Aug 2025; the CAEP document's own reference to SSF points at the unversioned `openid-sharedsignals-framework-1_0.html` URL (V), while search shows a `-final` URL. Confirm the announcement date.
12. **OAuth 2.1 vs RFC 9700.** 9700 (Jan 2025) says 2.1 will incorporate it; the 2.1 draft is at -16 (Sep 2026, S) and still an Internet-Draft — do not cite it as normative.
13. **RFC 6750 `invalid_token` for "revoked"** (SHOULD 401) vs real-world gateways returning 403 or 404 — SHOULD-level only.
14. **Rotation replay:** 9700 describes the AS "will revoke" the active RT on replay, but also notes it cannot tell which party replayed; many servers add grace periods — not covered by any text read.
15. **ASVS 5.0.0 V7.4.1/V7.4.2 vs RFC 9068/RFC 7009 (second pass).** The OAuth RFCs make JWT-AT survival until `exp` conformant; ASVS V7.4.1 (L1) says terminated sessions/self-contained tokens must stop working. Different scopes (access tokens issued to third-party clients vs the application's own session) — resolved by profile (SV-046), but vendors often describe both as "the token" (STD-029).
16. **OIDC Core §2 NOTE — ID-token `exp` is unrelated to session lifetime** vs. RFC 6749/9068 where token expiry bounds the credential: do not carry AT-style reasoning to ID tokens (SV-052).
17. **Metadata ownership.** `end_session_endpoint` and the logout booleans are *not* in OIDC Discovery §3 or RFC 8414 §2 (V) — they live in the logout specs; Discovery's example lists `check_session_iframe` and `end_session_endpoint` anyway. A client that validates metadata against the base lists alone will mis-flag them as unknown.
18. **Two well-known locations.** RFC 8414 (insert) vs OIDC Discovery (append) differ for issuers with a path component; both must be tried (SV-054).
19. **`invalid_grant` is overloaded** (invalid, expired, revoked, foreign client; reuse) — RFC 6749 §5.2 (S) gives no way to tell why; RFC 9700's reuse-detection and ASVS V10.4.5 revocations are therefore invisible except via follow-up probes.
20. **Core `offline_access` vs Back-Channel §2.7** — `offline_access` RTs are *not* tied to the browser session (consent-based, S); BCL says they "normally SHOULD NOT be revoked" on logout. ASVS V10.4.9 requires the user to be able to revoke them via the AS UI (a different event than logout).
21. **RFC 6455 silence vs ASVS V4.4.4/V7.4.1:** the protocol is silent on re-authentication; ASVS expects session-level termination semantics to cover WebSocket sessions. Treated as profile-dependent (SV-055).
22. **Date resolution vs `exp` precision:** `exp` is a NumericDate (may carry fractions, usually integer seconds); `Date` is whole seconds; combined timing uncertainty ≥ ±1 s — below any practical leeway but non-zero (SV-047).
23. **Core errata set 3.** A "draft 36 incorporating errata set 3" exists in search results while the Final page read is errata set 2 (15 Dec 2023); text read here may change in a future final-with-errata-3.
